# Forma Design System Agent Usage

Status: canonical local usage instructions for coding agents.

## Purpose

Agents working in Echelon applications must use Forma in this repository as the source of reusable interface presentation before creating application-local controls or interaction styling.

The Forma component showcase is a discovery surface. The canonical implementation remains the repository source:

- `patterns/*.html`;
- `dist/tokens.css`;
- `dist/foundations.css`;
- `dist/components.css`;
- `dist/assessment.css`;
- component and assessment manifests.

## Required agent sequence

1. Identify the interaction semantics before choosing a visual treatment.
2. Search the component showcase or `patterns/` for an existing canonical pattern.
3. Prefer native HTML semantics over custom behavior.
4. Import the design-system CSS layers rather than copying token values into the application.
5. Copy the canonical pattern markup and preserve its accessibility structure.
6. Keep meaningful application state and legal transitions in the application/Ordo layer.
7. Add Limen behavior only when the browser-native component cannot provide the required behavior.
8. Do not place JavaScript, Custom Elements, framework runtimes, or WebAssembly inside a design-system component.
9. Do not infer scoring, authority, applicability, completion, obligations, or domain meaning from visual order, color, labels, or selection position.
10. Validate keyboard, pointer/touch, screen-reader semantics, zoom/reflow, reduced motion, forced colors, and supported browsers.
11. If no pattern fits, document the missing semantic need before adding a new pattern.
12. If a new pattern is added, add showcase metadata, browser tests, accessibility coverage, documentation, and ROS attribution in the same change.

## Public CSS imports

Use the package surface:

```css
@import "@echelon-foundry/design-system/tokens.css";
@import "@echelon-foundry/design-system/foundations.css";
@import "@echelon-foundry/design-system/components.css";
@import "@echelon-foundry/design-system/assessment.css";
```

Applications may use `all.css` when a single combined stylesheet is preferable.

## Component selection rules

### Use a native element directly when it already expresses the required semantics

Examples include:

- ordinary buttons;
- links;
- text fields;
- checkboxes and radios;
- select;
- details/summary;
- dialog;
- progress;
- range;
- number input.

The design system may style these elements or define a composition around them, but it does not replace native semantics for novelty.

### Use a canonical pattern when several elements must be composed consistently

Examples include:

- ordinal scales;
- question shells;
- validation summaries;
- ranking;
- allocation;
- rule builders;
- obligation panels;
- matrix questions;
- semantic differentials;
- hierarchical choice.

### Use Limen when coordinated behavior is required

Examples include:

- ranking movement and announcements;
- aggregate allocation validation;
- dual-thumb range enhancement;
- cardinality/exclusive-option enforcement;
- complex combobox/search behavior;
- rule-builder editing;
- best/worst cross-column exclusion;
- hierarchy cascade policy.

Limen behavior consumes and projects application state. It does not move authoritative state into the component package.

## State and authority rules

The component layer may own only native/presentation state such as:

- checked;
- selected;
- open;
- disabled;
- focus;
- hover;
- local disclosure;
- native form validity;
- application-rendered `data-ef-*` presentation markers.

The application/Ordo layer owns:

- legal transitions;
- domain validation;
- scoring;
- applicability;
- completion;
- capabilities;
- obligations;
- persistence;
- authorization;
- effect policy;
- unknown outcomes.

## Accessibility rules

Do not remove or weaken:

- `fieldset` / `legend` grouping;
- visible labels;
- accessible names;
- native control roles and values;
- focus-visible treatment;
- keyboard paths;
- direct-entry alternatives to drag;
- non-color state cues;
- special-answer separation;
- narrow/mobile decomposition;
- reduced-motion behavior;
- forced-colors support.

A visually cleaner implementation is not an improvement if it weakens these contracts.

## Styling rules

- Use design tokens and public classes.
- Do not hard-code a new local palette when a semantic token exists.
- Do not fork a component solely to change spacing, color, or typography.
- Do not use visual order as scoring order.
- Do not depend on icons or images as the only semantic channel.
- Preserve the Echelon Foundry visual language unless the consuming product has an approved product-specific layer.

## Showcase rules

The site is generated by `site/build-site.mjs`.

Every canonical `patterns/*.html` file must have showcase metadata. The generator produces:

- one component page per canonical pattern;
- at least three live examples per page;
- visible source markup;
- static, zero-runtime HTML/CSS output.

Do not hand-edit `site-dist/`. It is generated output and is not committed.

When adding a new pattern:

1. add the canonical pattern;
2. add metadata in `site/build-site.mjs`;
3. add/update CSS;
4. add browser and accessibility tests;
5. run `npm run site:check`;
6. inspect the generated page;
7. complete ROS attribution.

## Validation commands

```bash
npm run build
npm run test:runtime
npm run test:tokens
npm run test:browser
npm run site:build:only
npm run site:test
./ros registry check
./ros validate
```

For a full local site build:

```bash
npm run site:build
```

For a local preview:

```bash
npm run site:serve
```

## Do not

- add component JavaScript;
- add Custom Elements to the package;
- add framework-specific component implementations as the canonical API;
- duplicate Likert/NPS/etc. when they are presets over an existing primitive;
- copy markup from rendered browser DOM instead of the canonical pattern file;
- create inaccessible drag-only or image-only interactions;
- silently change component semantics in an application;
- edit generated `site-dist/` output by hand.
